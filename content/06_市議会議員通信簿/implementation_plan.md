# 市議会議員通信簿 実行計画

「市議会議員通信簿_事前検討資料」および事前ヒアリング内容を基に策定した実行計画です。

## 1. プロジェクト前提条件・要件定義

- **目的（ゴール）**: 市民の「市政への漠然とした関心度」を高めること。
- **ターゲット**: これまで政治に関心が薄かった20〜30代の若年層＋真ん中世代。
  - **UI/UX方針**: 政治に詳しくない層でも直感的に理解できるよう、長文の羅列を避け、スマホでの閲覧に最適化します。パッと見て傾向がわかる視覚的なグラフ（レーダーチャートやワードクラウド等）を多用します。
- **評価・可視化の主軸**: 以下の2軸を併用し、多角的に議員の活動を可視化します。
  1. **注力カテゴリ**（福祉・教育・インフラなど）
  2. **議会での役割**（課題提起、修正提案、代弁など）
- **対象データ**: 過去1年分（2025年6月〜2026年3月）の議会議事録（主に一般質問を想定）。
- **運営体制・リスク管理**:

  - **体制**: 有志市民1名での運営。
  - **方針**: 個人運営のため運用コストを極小化できるよう、議事録の取得〜AI要約〜タグ付けの自動化パイプラインを強固に構築します。
  - **リスク管理**: 問い合わせ対応はメールのみに限定。サイトの目立つ位置（トップページ等）に「本サイトは公式データに基づくものの、AIを用いた自動要約等の実験的プロジェクトであり、完全性を保証するものではない」旨の免責事項を強調表示し、トラブルやクレームのリスクを抑制します。

### 一般質問を行っていない議員への対応方針

議員の中には、役職（議長・副議長など）の慣例や、委員会の活動を中心としているなどの理由で、本会議での一般質問を行っていないケースがあります。単に「データなし」と表示すると、有権者に「活動していない」という誤解を与えるリスクがあるため、以下の対応を基本方針とします。

1. **役職等による構造的理由の明記**: 議長や副議長など、議会運営の慣例上、一般質問を行わない役職にある場合は、プロフィールやグラフ部分にその旨をはっきりと明記し、市民にコンテキスト（背景）を提供します。
2. **ニュートラルなUI表示（Empty State）**: 役職以外の理由で一般質問を行っていない場合でも、単なる空欄や「0点」といったネガティブな見え方は避け、「対象期間内（2025年6月〜2026年3月）の一般質問：なし」という事実をフラットに記載するUIを設計します。
3. **（将来的な拡張を見据えた設計）**: 初期フェーズでは対象外としますが、将来的には委員会での発言や、議案に対する賛否の採決結果などを追加し、一般質問以外での活動も可視化できる拡張性を持たせたページ構造にします。

## 2. 実行フェーズとタスク

### フェーズ1：技術的実証（PoC）の実施
システム全体を構築する前に、AIを用いた自然言語処理の精度と有用性を検証します。
- [ ] **対象データの選定**: 2025年6月〜2026年3月の議事録から、数名分の一般質問をサンプリング。
- [ ] **要約・構造化の検証**: 「①課題の背景」「②主張・提案」「③市側の回答」の3要素へ安定して構造化できるかAIプロンプトの調整。
- [ ] **分類ラベルの検証**: 「分野別カテゴリ」と「役割別」の2軸で、意図した通りのタグ付けがAIにより機械的に可能か精度を測定。
- [ ] **出力結果の評価**: 生成された要約やタグが、特定の政治的バイアスを含んでいないか確認。

### フェーズ2：データ処理の実行（1名ずつの高精度処理）
- [ ] 精度を落とさないよう、全データを一括処理する自動化スクリプトではなく、「議員1名ごと」に手動または半自動でAI要約・タグ付けを実行し、結果を目視確認しながら進める運用フローを確立します。
- [ ] 処理した議員の通信簿データ（要約・分類結果）を順次ファイルに蓄積します。
- [ ] 透明性確保のため、プロンプトと評価基準（ルーブリック）の公開用ドキュメントを作成します。

### フェーズ3：UI/UX・フロントエンド設計
- [ ] スマホ最適化された「比較・ドリルダウン型」のダッシュボードを設計・実装（一覧ページ、議員個別ページ）。
- [ ] 一般質問を行っていない議員向けの「空状態（Empty State）」のUI設計と、役職等の補足説明の表示。
- [ ] 免責事項の明記と、メール問い合わせ窓口の設置。

## Verification Plan

- **AI精度の検証:** サンプリングした議事録とAIの出力結果を突き合わせ、意味の欠落やハルシネーション（事実無根の出力）がないか目視確認する。
- **ユーザビリティテスト:** プロトタイプ段階で、可能であればターゲット層（20〜30代・真ん中世代）に近い方に画面を見てもらい、直感的に活動内容が伝わるかテストする。
